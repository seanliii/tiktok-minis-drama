## 2. 证据和业务状态分开

1. 加密收件仍是追加记录，保存原始字节和验证时的签名，不公开导出。
2. 解析器不授权、不写库、不自行验签；只对受控收件中的原始内容做字段解析。
3. **最小关联证据不齐时挂起**，不是成功：至少能确定合同、事件语义和适用环境；创建／重新启用还须匹配本地操作。
4. 新操作可用 `order_id` 或已保存的 `trade_order_id` 定位；二者都提供时必须一致。不能认领该用户最近的另一笔交易。
5. 用户归属可由通知中明确的用户身份和已验证操作／合同核对；缺少用户字段时必须依赖已经建立的可信绑定，不能自行猜用户。
6. `is_sandbox` 明确时必须与接收环境及已有记录一致。缺失时不默认 false；只有同一应用、同一已验证合同／交易能提供确定环境时才可沿用该证据，否则保留待核对。
7. 同一交易、合同或操作被相互矛盾的身份／金额事实指向时记录冲突，不挑方便的一条覆盖。
8. 可选金额缺失显示未知，不把报价当实际扣款；金额保留字符串，不进行浮点换算。权益时间未知不阻止确认可核对的交易事实。

## 3. 数据模型与迁移

保持既有单集／整剧 `orders` 和 `entitlements` 不变。

- **合同绑定**：应用、明确环境、平台合同编号、内部用户、已验证身份、档位及绑定证据。用户归属不可转移；当前档位观察不覆盖历史交易的报价。
- **每期交易**：应用／环境／平台交易号唯一；合同、用户、本地操作可空、创建或续费类型、确认收件、原始金额／币种、原始权益期间；退款和撤销事实独立保存。
- **业务事件记录**：逐类保留创建、续费、取消等动作及来源收件。同一个动作的重复投递不重复记一笔付款；每次原始投递仍可审计。
- **处理结果**：每份收件的已记录、重复、待绑定、待环境核对、不支持、格式错误或冲突，以及受控重试时间。
- **操作确认扩展**：为现有 `subscription_operations` 追加可空的确认收件／时间及冲突字段。保留原技术执行阶段；对外状态可依据匹配收件显示“已确认”，不要把已创建改写成 `not_created`。
- 更新“每用户一个未决操作”的索引及查询，使已确认操作不再占用待办；迁移在事务中完成，不重置旧库。
- 恢复备份时只冻结尚无确认凭据的旧操作；已有确认和流水保留，当前权益仍重新查询平台。

## 4. 各事件处理

| 事件 | 处理 |
| --- | --- |
| create | 核对原操作和交易，绑定合同，记录首期，确认原操作；通知先于创建 HTTP 回执也能处理，迟到回执不得覆盖匹配确认 |
| renew | 用新的交易号记录新一期，绑定已有合同；乱序先到的通知保留，合同建立后重处理 |
| reactivate | 确认对应重新启用操作，记录动作；不自动增加一个收费期间 |
| cancel | 记录关闭续费动作，不把其新交易号当原付款订单，不撤已付观看 |
| onhold | 记录付款异常，刷新当前权益，不仅靠状态名撤权 |
| expire | 记录到期并使观察失效；晚到旧消息不覆盖新合同的实时有效资格 |
| refund | 记录对应历史交易的退款观察，不撤其他周期或当前合同；不把不明口径的多次金额相加 |
| revoke | 记录相应合同撤销和目标交易退款，强制核对当前资格；旧合同消息不能杀掉另一份新合同 |

付款、退款、动作、当前观看四者不混成一个“VIP 开关”。

## 5. 接线与运行

- 原 webhook 入口：先原始验签和持久接收，再尝试解析及原子入账；基础设施失败可重试，已保存原文不丢失。
- 合同可从匹配操作建立，也可从当前用户授权下的明确平台查询建立可信绑定；查询本身不能生成“已付”流水。
- 创建 HTTP 返回并保存交易号后，重处理已到达但待绑定的收件。
- 提供受控重处理函数及可停止的后台消费者；真实服务入口启动、退出时停止。不能在 import 时启动计时器，也不能绕过现有登录／来源检查。
- 管理端可查看处理结果、每期流水和退款观察；重处理只使用已有验证收件，不提供“手改已付”的接口。
- 用户可查看自己的已确认订阅历史。完成操作后核对当前观看并返回内容；金额未知或待核对时明确说明。
- 新增生产购买显式开关，默认关闭；测试和生产共用处理代码，仅使用各自的档位和环境。生产启用前必须完成实际官方联调和应用要求。
