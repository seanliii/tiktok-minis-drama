# 测试与正式共用流程

**2026-10-15：本轮继续解决“测试时看到什么，上线应当基本一样”的问题。** 不再给测试付款额外添加一次确认，也不再只用页面接口替身代表正式链路已经跑过。

原则：**同一套页面、订单和权益代码，区别在环境数据、平台权限及回执类型。**

## 1. 三种环境，不是三套产品

| 环境 | `DRAMA_MODE` | 用户身份与视频 | 付款与回执 | 默认数据目录 |
| --- | --- | --- | --- | --- |
| 本地联调 | `local` | 本地注册账号、私有上传视频 | 本地无真钱测试；与平台接入分开标注 | `.local/` |
| 预发布 | `staging` | 与正式相同的 TikTok 身份、平台媒体条件 | 必须实际启用平台测试权限；只接收明确 `is_sandbox=true` 的有效回执 | `.staging/` |
| 正式 | `production` | TikTok 身份、平台媒体条件 | 只接收明确 `is_sandbox=false` 的有效回执 | `.production/` |

预发布与正式都默认 `DRAMA_PAYMENT_MODE=disabled`，不因切环境就启用付款。两者都禁止本地注册、本地 `sandbox-confirm` 和本地视频入口，必须走正式的业务代码。

**重要：设置 `staging` 只影响我们自己的服务器，不会让 TikTok 自动免扣费。** 必须由平台实际提供测试权限及测试配置，再进行端内验证。不能在生产账号上靠改一个变量假装处于平台沙箱。

数据库记录所属环境；三种环境不能复用同一个库。拒绝混用时不会删除数据或自动迁移订单。测试会员、测试订单不能带入正式账本。

## 2. 一样的购买过程

```text
选择商品 → 订单页查看价格 → 点击一次「確認して購入」
    → 调用该环境的支付渠道
    → 查询我们的订单服务
    → 确认已付订单与该账号对应的观看权
    → 自动返回观看
```

- 订单页不再出现“先进入测试支付，再确认测试支付”的额外一层。
- 两种付款渠道调用后的订单查询、权益确认和自动返回使用同一个实现。
- 本地演示保留“不扣款”的提示；预发布显示环境提示，但不作“平台一定不会扣款”的承诺。
- 只是打开结算页、前端成功回调、按钮文字变化，均不会自行发放权益。
- 点击付款后按钮显示处理中，避免重复调用。付款响应丢失、短暂断网或权益暂未可见时，使用有上限的只读重查，不自动重新付钱。
- 旧订单从购买记录打开时可以查看状态和返回观看，不会因查看记录重复购买。

相关实现：`src/views/Checkout.vue`、`src/utils/payment.ts`。正式和预发布账号页只展示可用的 TikTok 登录入口，不再展示会被服务器拒绝的普通邮箱登录表单。

## 3. 平台支付补齐的能力

### 真实建单前先检查金额

后端先使用用户令牌调用官方金额检查接口，只有明确通过后才提交平台建单。价格始终由服务端确定；检查失败、超时或响应不完整时不发建单请求。

### 主动核对平台状态

- 用户订单页点击 **支払い状況を再確認**。
- 管理后台对平台订单点击 **核对平台状态**。
- 后端只使用数据库保存的该笔交易号，不接受客户端另外传入交易号或金额。
- 自动轮询仍读取自己的数据库；不会每两秒向 TikTok 发请求。
- 每订单查询合并并发，冷却 30 秒，错误也计入冷却，防止反复点击轰炸平台。

**平台查询状态与业务订单状态不同：**

| 平台核对结果 | 我们如何处理 |
| --- | --- |
| `PENDING` | 继续等待，不推断为取消或失败 |
| `SUCCESS` | 记录平台报告成功；缺少有效回执时仍不发观看权 |
| 无法确认 | 记录 `UNCONFIRMED`，不给出假成功，不泄露平台响应里的秘密 |

目前核对接口没有足够字段证明金额、退款细节及测试环境；它不是完整财务对账。有效支付／退款回执仍优先，主动查询不能覆盖已经处理的退款。

**真实平台取消订单接口未得到完整公开契约，未编造实现。** 本地取消不等于平台订单已经关闭；未确认的旧单不会被悄悄释放再卖一张。正式自动续费订阅、续费取消与恢复仍需继续实现和实测，不把本地限时 VIP 当成正式订阅。

官方参考：

- [Payment APIs](https://developers.tiktok.com/docs/en/minis-payment-apis)：金额检查、建单和 POST 查询接口。
- [IAP 接入](https://developers.tiktok.com/docs/en/tiktok-minis-in-app-purchases)：客户端回调、服务端验签与发货的边界。

## 4. 部署配置：同一程序启动两个独立环境

应用目录提供：

- `.env.staging.example` → 复制并填写为 `.env.staging`
- `.env.production.example` → 复制并填写为 `.env.production`

真实文件被 Git 忽略；密钥只填服务端变量，不能放进 `VITE_` 变量。

```bash
npm run build:fullstack
npm run check:staging
npm run start:staging
```

正式环境用对应的 `check:production`、`start:production`。两者使用**同一个启动脚本和同一份服务构建**，先验证环境、HTTPS 来源、管理员和密钥配置，再启动。`check` 只校验配置，不创建数据库、不监听端口，也不证明平台权限已经就绪。

Minis 客户端分别使用：

```bash
npm run build:minis:staging
npm run build:minis:production
```

两者都用同一套前端源代码。区别由 `.env.staging` / `.env.production` 的 HTTPS API 地址决定；最终 App、Client Key、平台信任域名必须与所选应用一致。未配置真实 API 时生成的包只能做结构检查，不能直接上线。

## 5. 页面与 API 不同域名

服务器现在支持**显式配置**的跨域请求，不关闭原有请求来源、登录与权限检查：

```dotenv
# 写页面的 Origin，不带路径；管理页面来源也要包括
DRAMA_ALLOWED_ORIGINS=https://reader.example.com,https://api.example.net
DRAMA_COOKIE_SECURE=true
DRAMA_COOKIE_SAMESITE=none

# 这是公开的服务地址，不是密钥
VITE_API_BASE=https://api.example.net/api
```

- 同站部署可以继续默认 `strict`；跨站请求必须显式开启 `none` 并使用 Secure Cookie。
- 只允许精确来源，不能填 `*`、任意网站或 `null`。
- 预检方法和请求头有明确名单；跨域也不能绕过管理员、付费观看或草稿权限。
- 原登录限流、上传限额和私有视频授权不变。
- CORS 允许不代表浏览器一定接受第三方 Cookie。实际 TikTok WebView 的策略仍需真机检查；不能通过关闭浏览器安全保护制造“通过”。

### 本机真实 TLS 浏览器观察

本轮用页面正常 `fetch(credentials: 'include')` 触发登录，没有手动注入 Cookie 或 Origin：

| 测试环境 | Chromium | WebKit |
| --- | --- | --- |
| `https://localhost:5341` → `https://localhost:5342`，同站跨源 Strict | 登录、会话、创建内容、退出通过 | 登录、会话、创建内容、退出通过 |
| `https://localhost:5341` → `https://127.0.0.1:5342`，跨站 None | 本次建立会话 | **本次未保存第三方 Cookie**：登录响应 200，但后续仍未登录 |

**因此不能把“跨域测试用例执行完成”说成所有跨站部署都能登录。** 验证中对跨站策略的用例会记录接受或阻止；WebKit 被阻止是明确的部署限制，不是已经修好的登录能力。

部署优先选同站域名／反向代理方案。实际 TikTok 打包页面来源、WebView Cookie 策略和所需的会话传输方式尚需真实端内确认，不能凭桌面结果猜测。

## 6. 这次怎么验证，不再只看假接口

新增独立测试启动器会：

1. 创建 local、staging、production 三个临时业务数据库，启动真实编译后的服务。
2. 同时读取同一份前台、管理页和服务器构建，记录文件路径与 SHA-256，确认不是拿两份不同代码比较。
3. 页面自己发真实登录、建单、查询、播放资格请求。
4. 只在独立测试工具中替换外部 TikTok 令牌、金额检查、交易服务及 SDK／解码器；它不能直接调用发权函数或写业务订单表。
5. 付款结果通过本机真实 HTTP 回调、HMAC 验签、交易与环境匹配后进入数据库。
6. 检查错误签名、错环境回执、延迟、取消、重复回执、退款和账号隔离。

这叫**离线正式路径验收**，不是 TikTok 官方沙箱、平台审批或真正的短剧解码实测。测试工具与令牌不会进入生产入口。

运行全套：

```bash
npm run test:all
```

阶段验收可分别使用现有 `test:unit`、`test:server`、`test:admin`、`test:fullstack`，以及 `test:platform-path`、`test:cross-origin`。三路径测试先需要一次 `build:fullstack`，不要与构建并发修改产物。TLS 浏览器测试独立启动临时 HTTPS，不读取正式配置，也不放宽浏览器的跨域／Cookie 保护。

最终结果以 [009 本轮记录](/progress/updates/2026-10-15-009-environment-parity)为准。此前 331 项是上一版的测试记录，不挪作本轮新增功能已通过的证据。
