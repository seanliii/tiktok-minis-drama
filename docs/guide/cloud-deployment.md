# Aurora 云部署选型：先东京，不先买三套

调研时间：**2026-10-15（北京时间）**。目标应用仍为 **Aurora Drama**，App ID `7670022867891177493`，主体 `7669964115334611988`。日本先发，韩国和东南亚以后分批开放。

**本页是源码核查、官方价格核查和采购建议，不是已部署记录。没有购买云资源，没有开通收费服务，没有提审、发布或真实扣款。**

## 1. 直接结论

- **需要部署业务后端。** TikTok 只收前端代码包，不代表它替本项目运行账号、订单、观看权益、片库和运营后台。
- **建议先用阿里云东京的一台 4 vCPU／8 GiB ECS，按月购买。** 前提是团队没有更合适的现成云环境；已经用 AWS 的团队不必为了这个项目换云。
- **本次建议是在线联调／小流量起步配置，不是高可用正式收费架构的验收结论。** 没有日韩东南亚实网延迟测试，也没有该规格的并发容量压测。
- **视频另走平台要求的视频云和播放器。** 业务服务器管“谁能看哪一集”，BytePlus／TikTok 管媒体托管、审核和播放；不买 GPU，不让服务器中转所有观众的视频流量。
- **不能把“服务器买好”当作“开发只剩填密码”。** 媒资同步、完整真实订阅和部分部署工作仍未实现。

## 2. 为什么现在选东京，后续怎么扩

下面是根据“日本先发”提出的部署建议，不是声称东京对每条亚洲网络线路都最快。AWS 官方也建议把业务资源放在主要用户附近。[S3]

| 业务阶段 | 建议 | 不做什么 |
| --- | --- | --- |
| 现在：日本首发 | 东京一套业务服务和数据库；日本真机先验收 | 不为未开放市场提前买服务器 |
| 加入韩国 | 先测试韩国用户访问现有东京 API 的延迟和稳定性，再决定是否加首尔节点 | 不仅凭地图距离承诺体验 |
| 东南亚形成主要流量 | 比较新加坡和各目标国的实际访问结果，再决定迁移或增加区域服务 | 不把“东南亚”当成一个语言、市场或统一网络 |
| 开始明显投放或要求故障不停服 | 先完成共享数据库／存储及多实例改造，再增加应用节点 | 不复制多份 SQLite 让各地各记一套订单 |

API 服务器位置和视频分发位置不是一回事。视频应由媒体服务向观众分发，不能拿普通 API 主机的公网带宽代替完整的视频分发方案。[S4][S5]

每个新市场还需要语言、字幕、版权地域、定价、客服和平台发行设置；数据存放与跨境处理要求应让运营／法务按目标国家确认。选东京或新加坡不能替代这些确认。

## 3. 现在可以照着选的配置

以下是**采购建议**，还未下单；具体实例库存和磁盘兼容性需在对应账号购买页确认。

| 项目 | 建议 |
| --- | --- |
| 云厂商／地域 | 阿里云，Japan (Tokyo)，东京 |
| 机器 | 1 台 ECS，x86_64，4 vCPU／8 GiB；`ecs.c7.xlarge` 作为本次可核查的参考型号 |
| 系统 | Ubuntu 24.04 LTS；运行项目支持的 Node.js 24，版本固定并在 Linux 上验证 |
| 磁盘 | 40 GiB 系统盘＋100 GiB 持久化数据盘；ESSD PL0 或购买页支持的同档持久化云盘 |
| 网络 | 先按出网流量计费、设合理峰值和账单告警；50 Mbps 可作为起步峰值配置，不是每月无限流量 |
| 域名与 HTTPS | 一个受控域名，管理页和 API 同域；Minis 使用实际 HTTPS API 地址 |
| 数据 | 首轮联调使用独立 SQLite 数据目录，不复制开发测试库冒充正式库 |
| 备份 | 独立私有备份存储＋一致性备份与恢复演练；备份不能只留在同一台机器上 |
| 购买周期 | 先一个月或按量，验证后再考虑长周期 |
| 暂不采购 | GPU、视频转码服务器、Kubernetes、多地域数据库、Redis、大额固定公网带宽 |

这台主机运行 API、管理网页和初期数据库。**正式视频不长期堆在这 100 GiB 数据盘，也不通过它分发给所有观众。** 当前封面／字幕仍是本机文件，未完成对象存储接入前必须保留持久化磁盘。

如果仅为短期低成本测试，2 vCPU／4 GiB 也可作为候选；是否足够仍要在目标云机器上测。4 vCPU／8 GiB 是留出构建、管理操作及接口处理余量的起步建议，不能换算为已验证的日活或在线人数。

### 未来正式收费的部署取舍

当前单机有故障停服风险，不宣称高可用。公开收费前至少完成备份恢复、真实登录支付、媒资和安全验证，并明确可接受的停机与数据恢复目标。

如果团队要求机器故障时用户仍能购买，建议在正式推广前采用**同地域两个应用节点＋共享关系数据库的高可用配置＋负载均衡**。数据库可评估托管 PostgreSQL，先以 2 vCPU／4 GiB、50–100 GiB 作为报价候选，再按测试调整；**项目目前没有 PostgreSQL 接入，不能立即购买后只改连接串。** 迁移范围、费用和上线窗口需另行确认。

测试与正式继续共用业务代码，但域名、数据库、平台凭据和付款环境必须分开。不要为了节省一台机器的费用把测试数据混进正式订单。

## 4. 官方价格和预算口径

### 主机对比

阿里云数据来自当天实际打开官方动态价格页、分别选择东京／新加坡并筛选同一个型号；AWS 来自官方 Lightsail 价格页。[S1][S2]

| 方案 | 配置 | 公开月价（美元） | 口径 |
| --- | --- | --- | --- |
| 阿里云 ECS 东京 | `ecs.c7.xlarge`，4 vCPU／8 GiB | **115.09** | 月付机器费，磁盘和网络另计 |
| 阿里云 ECS 新加坡 | 同型号，4 vCPU／8 GiB | **98.65** | 同上；不能为省这部分费用忽略首发用户体验 |
| AWS Lightsail 通用型 | 2 vCPU／8 GB、160 GB SSD | **44** | Linux、带公网 IPv4 的套餐，含一定流量 |
| AWS Lightsail 通用型 | 4 vCPU／16 GB、320 GB SSD | **84** | 同上；不是与 ECS 完全相同的性能条件 |

Lightsail 的通用套餐有 CPU 基线及突发容量规则，不能把便宜套餐的 vCPU 数当作持续满负载性能保证。[S6] 它适合预算优先的起步方案；如果团队已用 AWS，可优先评估，无需换成阿里云。

上述是**公开参考价，不是含税成交价**。阿里云为国际站口径，库存、账号合同、折扣、税费以及网络计费方式以购买页为准。不把按年付款折算的月价冒充随时可取消的月付价格，也不计入不确定的新客优惠。

### 东京起步账单示例

同一官方价格页，东京 ESSD PL0 月付参考为 **0.076 美元／GiB**；普通出网按量参考为 **0.087 美元／GB**。例如：[S1]

```text
4 vCPU / 8 GiB ECS                 115.09 美元 / 月
40 + 100 GiB ESSD PL0               10.64 美元 / 月
假设当月普通 API 出网 100 GB          8.70 美元 / 月
上述小计                            134.43 美元 / 月
```

100 GB 是预算假设，不是测得的用量。再为公网 IP、备份、日志和费用波动留余量，**建议起步业务基础设施先预留 150–200 美元／月**。这是规划预算，不是厂商承诺；**不含 BytePlus 视频费用、开发费用、版权、投放、税费，也不含后续托管数据库和双节点高可用费用**。

如果选择固定带宽，东京 5 Mbps 的官方参考为 18.48 美元／月，但它是容量限制，不能等同于视频分发能力；超过 5 Mbps 的固定带宽价格也不是简单线性延长。[S1]

## 5. 视频费用必须单独算

TikTok 官方要求本类短剧接入媒体资产管理和指定播放器。当前项目应该先确认已有 BytePlus 合同、账号与可绑定空间，再开通，避免重复买一套普通视频点播。[S4][S5]

BytePlus 的公开计费包含媒体存储、处理／转码、分发及可能的播放器相关费用，实际以本主体和 TikTok 集成适用合同为准。[S7][S8]

- 官方标准存储参考为 **0.017 美元／GiB／月**：稳定存 500 GiB，单存储示例为 **8.50 美元／月**，不是全包视频价。
- 官方的 **0.08 美元／GB** 是**未使用 VOD CDN 加速时的存储出网**，不能把它当成日韩东南亚所有播放的 CDN 统一价。
- 播放成本应按实际观看量、平均实际码率、地区分布、转码输出和合同单价预算。

**流量示例，不是实际业务预测：**

```text
每天 1,000 人 × 每人观看 10 分钟 × 30 天
× 平均 2 Mbps ÷ 8
= 约 4,500 GB / 月，即 4.5 TB（十进制）
```

这个估算未计入预加载浪费、协议开销、重试等。它解释了为什么不能只拿主机月费当短剧产品总成本。BytePlus 最终空间、分发区域和费用应在首次正式上传前确认，并设置告警。

用户已确认 11988 主体流程完成，本页不重复要求办理主体。以下是 **Aurora 应用和本项目服务** 的状态。

| 项目 | 2026-10-15 核查结果 | 下一步 / 责任 |
| --- | --- | --- |
| App 基本信息 | 当前代码版本仍因基本信息审核不能送审；应用资料有待填项 | 管理员提供真实资料，开发协助填表；主体审核不能替代 App 审核 |

| 媒资服务 | 登录后的 Aurora「行业解决方案」显示 **媒体资产管理：未激活** | 管理员确认账号合同并激活，开发完成媒体登记、审核和上下架同步 |
| 真正上传上线流程 | 现有管理页主要上传本地文件；生产发布要求真实平台 ID 和审核状态 | 仍需开发云端上传／导入、剧集登记和审核结果写回，不能直接手填“已过审” |
| 用户登录 | 已有 TikTok 授权码换身份、令牌存储和会话代码 | 填 Aurora 密钥、来源和域名，验收实际端内 Cookie；不是只测本机 |
| 单集／整剧付款 | 已有平台建单、回执验签、权益、退款回执等代码 | 配好商品和通知地址；真实端内验证取消、重复通知、延迟、退款及重复购买 |
| VIP 自动续费 | 服务端当前明确拒绝真实 VIP 订单 | 仍需订阅创建、续费、取消、到期与权益同步开发；先不冒充可售商品 |
| 运维 | 本次范围内未发现完整反代、服务管理、备份恢复和版本化迁移方案 | 开发补自动启动、HTTPS、可信代理、日志告警与恢复演练 |
| QA | 没有本次目标云规格压测及日韩东南亚实际线路数据 | 日本 iOS／Android 首先验收，其他市场开放前分别测试 |

**重要的部署适配问题：**当前服务按请求 IP 限流，但 `trust proxy` 是 `false`。加 Nginx 等反代后若不按真实拓扑修正并测试，用户可能被当成同一个代理 IP 共用额度。不能靠关掉限流或无条件信任所有转发头解决。

跨站 Cookie 同样需要真机验证；设置 `SameSite=None; Secure` 不是所有 WebView 都保存第三方 Cookie 的保证。若平台实际策略阻止，要根据官方支持方式改认证接入，不绕过浏览器规则。

## 7. 推荐执行顺序

1. **采购前**：确认现有云账号、域名及 BytePlus 账号／合同；没有现成资源时再按东京起步配置报价。
2. **云端测试环境**：修复可信代理适配，部署 HTTPS API 和管理页，设置独立数据目录、密钥、监控及备份。
3. **先跑一部合法日文剧**：激活媒体管理，打通上传／导入 → 平台登记 → 审核 → 播放，不绕开生产校验。
4. **完成登录和单次付费**：真机授权、通知、权益、退款和重试验收；真实订阅另补开发和验证。
5. **替换前端 API 地址并上传新版本**：扫码测试这个具体版本；保留原版本，不把上传成功当成业务通过。
6. **上线前**：补齐 App 审核资料，确定单机风险或高可用方案，完成容量和恢复测试，再由发布负责人提审。
