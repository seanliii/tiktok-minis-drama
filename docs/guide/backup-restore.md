# 本地数据备份、校验与换目录恢复

本工具用于搬走 **tt-minis 的业务数据库与本地上传文件**，并在另一个全新目录进行恢复演练。它不是整机迁移工具，不迁移浏览器资料或 Codex 对话，也不负责发布、启动服务或请求外部平台。

入口：`/Users/xuan/Desktop/cursor/tiktok/app/tt-minis/scripts/data-backup.mjs`。直接用 Node 执行，不需要安装依赖，不需要修改 `package.json`。换电脑后，把命令中的应用路径改为新机器上的实际路径。

## 1. 先明确备份范围

| 会保留 | 不会带走 |
| --- | --- |
| SQLite 快照里的用户、密码哈希、剧目、剧集、订单、权益、业务设置和平台业务记录 | `.env`、`.env.production` 等环境文件 |
| 数据库中的环境标记 `runtime_environment` | `admin-credentials.txt` 等管理员明文凭据文件 |
| 数据库中的加密平台凭据及其他加密业务状态 | 加密这些内容所需的环境密钥 |
| 快照中 `assets` 表引用的 `uploads` 直接子文件 | 资产表未引用的文件、子目录、日志、浏览器配置与 Cookie 文件 |
| 数据库里的 VOD 标识和关联记录 | **VOD 服务上的远端视频文件** |

**登录状态和短期下载授权不搬家。** 仅在备份的独立快照中清空 `sessions`、`session_transports`、`session_origins`、`playback_grants` 和存在时的 `media_export_grants`，并清理删除后残留的数据库空闲页。源库中的会话和授权不变；恢复后管理员和用户须重新登录。业务订单与权益不因此删除。

管理员原密码仍对应数据库里的密码哈希，但原密码明文文件不在备份中。请事先在可信密码管理器中保存凭据；不要等恢复后再寻找被明确排除的明文文件。

**新增订阅记录的恢复规则：** 源库与备份保持原始快照；仅在恢复的新目录，将**尚无匹配确认凭据**的未完成订阅操作改为待核对，保留原操作／交易编号，不重放创建或 SDK。已有确认凭据、每期流水、冲突和退款标记保留。报价和当前会员观察同时过期，须重新查平台；已付单集订单与永久购买权益不会被删除。原因是快照生成后，旧服务器可能已继续执行，不能把旧快照当作“从未发送”。历史付款也不等于当前仍有观看资格。见[订阅操作与恢复说明](/guide/subscription-workflow)。

## 2. 运行前提

- 标准 Node **22.13+ 的 22.x，或 24.x**。命令本身只使用 Node 内置模块。
- 使用 macOS/Linux 上支持真实 POSIX 权限和 SQLite 文件锁的本地文件系统。直接运行于 Windows 会拒绝；本轮没有验收 Windows/WSL、网络盘或不保留权限的文件系统。
- 所有目录参数必须是**绝对路径**。不能有独立的 `.` / `..` 路径分段、反斜杠或控制字符；路径本身及其父目录不能是符号链接。`.local` 这样的普通目录名不受点号限制。
- 父目录必须预先存在；**不要提前创建备份目录或恢复目录本身**。已有空目录、普通文件、符号链接及失效链接一律拒绝。
- 备份目标不能放进源数据目录。恢复目标不能放进备份目录或清单记载的原数据目录。`TMPDIR` 也不能指向这些受保护的输入目录。
- 显式填写 `--environment local`、`staging` 或 `production`。它必须同时符合数据库标记、备份清单和当前 shell 中已设置的 `DRAMA_MODE`。
- 工具不读取 `.env`，不使用 `DRAMA_DATA_DIR` 猜测源目录，也不会默认打开真实 `.local`。
- 源目录、备份目录及目标父目录应由可信账号控制。不要让其他进程同时搬动、替换或修改这些目录。工具拒绝可检测到的链接和读写变化，但不宣称能隔离同账号恶意进程或不可信文件系统。

工具创建的目录为 `0700`，文件为 `0600`。这只是访问权限，**不是加密**；数据库和清单仍是敏感文件。跨机器传输、离机存放与加密介质由操作者另行安排，工具不上传或外发任何内容。

## 3. 备份命令

下面 `/absolute/path/...` 都是占位路径，必须替换；示例不会自动发现数据。`BACKUP` 的父目录应已存在且由你控制。

```bash
APP=/Users/xuan/Desktop/cursor/tiktok/app/tt-minis
SOURCE=/absolute/path/to/private-data
BACKUP=/absolute/path/to/private-backups/backup-2026-10-16

node "$APP/scripts/data-backup.mjs" --help
```

### 在线备份：应用保持运行

```bash
node "$APP/scripts/data-backup.mjs" backup \
  --source "$SOURCE" \
  --output "$BACKUP" \
  --environment local
```

在线 WAL 库必须已有真实、完整的 `drama.sqlite-wal` 和 `drama.sqlite-shm`。备份期间可以正常新增业务和上传文件，但不要启动/停止其他数据库进程、删除旧媒体、移动源目录或重写已经上传的文件。

此模式通过 **只读 SQLite 连接执行 `VACUUM INTO`** 获得事务一致的独立快照，不用文件复制去拼凑活跃的数据库和 WAL。随后只从这份快照读取资产表。因此，“拍完账本照片之后才入库的文件”不会被错误地塞进先前的备份。

SQLite 读快照建立时已提交的业务记录会进入快照；之后的新提交不承诺包含。本工具不是持续复制或增量日志归档。长期读快照期间，应用的 WAL 可能继续增长，应预留磁盘空间。

### 停机备份：显式使用 `--offline`

先正常关闭应用和所有写入者，确认它们不会被服务管理器自动重启，再执行：

```bash
node "$APP/scripts/data-backup.mjs" backup \
  --source "$SOURCE" \
  --output "$BACKUP" \
  --environment local \
  --offline
```

`--offline` 是操作者对“全部写入者已停止”的明确确认。工具会拒绝任何残留的 `-wal`、`-shm` 或 `-journal`，检查源文件读取前后的身份、大小和修改时间，把干净的停机主文件复制到私有临时区，然后由 SQLite 生成、清理和验证快照。**这个分支绝不复制活跃 WAL 库的主文件。**

为什么不自动判断？正常停机后，数据库文件仍可能标记为 WAL 模式；直接只读打开它也可能在源目录新建 WAL/SHM。显式离线分支避免了这类源目录写入。它不能替代进程级停机安排：如果无法保证写入者停止，应使用在线模式。

若残留日志来自崩溃，请由应用按原环境正常恢复数据库并关闭，或保持其在线后再备份。**不要手动删除 WAL/SHM 来让离线检查通过。**

### 保存成功指纹

退出码 `0` 且输出如下，才表示命令成功：

```text
备份完成；请独立保存下面的清单指纹。
MANIFEST_SHA256=<64位十六进制值>
```

把这个值与备份时间、环境、应用代码版本、操作结果一起记录在**独立可信位置**，例如受控的交接记录或密码管理器。不要只在备份目录内保存它。

## 4. 校验：使用原先独立保存的指纹

```bash
PIN='替换为备份成功时独立保存的64位指纹'

node "$APP/scripts/data-backup.mjs" verify \
  --backup "$BACKUP" \
  --environment local \
  --manifest-sha256 "$PIN"
```

校验会逐项检查：

1. 清单的 SHA-256 是否符合独立保存的可信值，格式及版本是否受支持。
2. 备份目录是否只有 `manifest.json`、`drama.sqlite`、`uploads/`，媒体是否与清单一一对应。
3. 目录、文件、全部父路径的安全性和备份权限；拒绝符号链接、媒体硬链接、跨大小写冲突及嵌套媒体路径。
4. 数据库文件和每个媒体文件的大小及 SHA-256。
5. 将数据库复制并核验到私有临时区后，检查它不依赖 WAL，再执行 SQLite 完整性及外键检查。不会直接在待校验备份目录中打开 SQLite 或新建辅助文件。
6. 数据库环境和每条资产记录是否与清单相符；是否仍含被排除的会话；是否含本应用不需要的触发器、视图或虚拟表。

**不能从眼前这份待校验清单重新计算一个指纹，再拿来当作“可信值”。** 那样只能证明包内自洽，不能发现文件与清单被一起替换。若原指纹丢失，工具不会提供绕过选项；应从可信原始数据重新备份，或先按组织的安全流程确认来源。

校验成功表示本地备份的结构和内容符合检查，不代表来源身份已经通过数字签名认证，也不代表第三方平台、支付或远端 VOD 已验收。

## 5. 换目录恢复

在新电脑上准备好应用代码及相同的运行环境，将备份通过另行安排的安全方式送达。代码路径与数据路径可以改变；备份文件和原指纹必须对应。

```bash
TARGET=/absolute/path/to/new-private-data

node "$APP/scripts/data-backup.mjs" restore \
  --backup "$BACKUP" \
  --target "$TARGET" \
  --environment local \
  --manifest-sha256 "$PIN"
```

- 工具独占创建全新目标目录，不覆盖、合并或“清空后复用”已有目录。
- 先执行完整备份校验；写入目标时再次根据清单校验复制的文件。
- 在单个事务里把所有 `assets.storage_path` 改成新目录下的绝对路径。资产主键、文件内容和原环境标记不改变。
- 提交事务后重新打开数据库，校验环境、资产路径、完整性及外键；再次检查目标媒体哈希。
- 所有复制、校验、刷盘和临时文件清理成功之后，才写入 `restore-complete.json`。

恢复结果：

```text
new-private-data/
  drama.sqlite
  uploads/
    <资产表引用的单文件>
  restore-complete.json
```

完成记录包含原备份的清单指纹，以及路径改写后的数据库大小和 SHA-256。**恢复后的数据库哈希不同于备份中的哈希是正常现象**，因为绝对路径已改变。

然后由操作者显式把服务的 `DRAMA_DATA_DIR` 指向 `TARGET`，保持原 `DRAMA_MODE`，单独配置密钥，再启动并重新登录。不要直接移动已经恢复好的目录；再次换路径应再次执行恢复或重新备份。

`restore-complete.json` 是本次恢复的验收记录，不是新备份的 `manifest.json`。服务启动后会再次写库，完成记录中的数据库哈希也会随之过期；需要新备份时请对当前数据重新运行 `backup`。

## 6. 生产密钥与部署恢复演练

### 生产密钥必须单独安全迁移

- 原 `TOKEN_ENCRYPTION_KEY` 等解密密钥、TikTok 应用凭据、Webhook 验签秘密、BytePlus 凭据、管理员登录凭据，必须经独立的安全渠道交接。
- 工具不读取、导出或发送这些环境变量及配置文件。
- 数据库中的密文仍会保留；随意换成新加密密钥，不会自动把旧密文重新加密，也不会自动恢复可用状态。
- 不把密钥贴进工单、聊天、测试报告或命令日志。是否轮换密钥及如何处理历史密文应另行安排。

### 环境不是一个可以随意换的标签

`local` 备份不能恢复成 `staging` 或 `production`；生产备份也不能改成测试库。未标记的旧库会拒绝，不会被备份工具自动认领或修改。

正式恢复演练应使用隔离主机/容器与全新目录，保持 `production` 标记，并在启动应用之前限制外连、生产回调和任何实际平台写操作。**工具本身不联网，但你随后启动的应用可能联网。** 不要通过篡改数据库标记把生产账本伪装成本地数据。

### 演练记录建议

1. 记录应用代码版本、Node 版本、环境、备份开始/结束时间、成功指纹。
2. 在隔离目录运行 `verify` 和 `restore`，保留退出码及不含秘密的状态输出。
3. 核对环境标记、代表性订单和权益、剧集关联；用应用实际资产读取入口验证图片/字幕/本地媒体可找回。
4. 独立完成密钥、域名、HTTPS、登录、平台权限和远端 VOD 的核验。不要把这份本地演练当作真实支付或平台恢复已经通过。
5. 记录恢复耗时和仍需人工处理的步骤，据此确定可接受的数据损失窗口与恢复时间。

清单 `createdAt` 是生成清单的时间，不是精确的 SQLite 读事务建立时间。评估数据恢复窗口时应结合命令开始/结束记录，不要把清单时间当成“此刻之前的所有新写入都已备份”。

## 7. 失败处理与边界

所有失败均使用非零退出码和固定错误码，不打印文件内容、数据库记录、SQL 错误原文、源目录或秘密。Node 22 可能额外打印自身的 SQLite 实验性提示，它不是测试失败。

| 常见错误码 | 处理方式 |
| --- | --- |
| `DESTINATION_EXISTS` | 选择一个全新目标，先核对已有目录用途，工具不提供 `--force` |
| `ENVIRONMENT_MISMATCH` | 核对数据库标记、命令环境和当前 `DRAMA_MODE`；不要改标记绕过 |
| `OFFLINE_REQUIRED` | 正常停止全部写入者后使用 `--offline`，或保持应用在线 |
| `OFFLINE_UNSAFE` / `WAL_UNAVAILABLE` | 交由原应用恢复或正常关闭；不要删日志 |
| `MANIFEST_MISMATCH` | 备份与独立指纹不对应，停止恢复并核对来源 |
| `FILE_MISMATCH` / `MISSING_FILE` | 文件被改、复制不完整、原媒体缺失或读取中发生变化，重新取得完整备份 |
| `UNSAFE_PATH` / `UNSAFE_PERMISSIONS` | 核对真实物理路径、链接、目录重叠和访问权限 |
| `DATABASE_INVALID` / `ASSET_MISMATCH` / `UNSAFE_SCHEMA` | 保留原数据，调查库或清单异常；不要跳过校验 |
| `MANIFEST_INVALID` | 清单格式不受支持、损坏或超过 16 MiB；不会交付一个无法再次校验的“成功”备份 |
| `IO_ERROR` | 检查剩余空间、存储和权限，修复后使用全新目标重试 |

正常捕获的失败会清理本次独占创建的目标，不会修改既有目录。断电、强制杀进程或清理权限失效时可能留下私有临时文件或未完成目标；没有成功指纹和有效完成清单的目录不能作为有效备份，也不能直接作为已恢复数据启动。不要在原位置强行续写，先核对残留内容，再用全新目标重做。

在线 SQLite 为读锁使用 SHM；访问时间和共享锁内存不属于业务内容不变的承诺。工具不向源库写业务、改环境、删会话或检查点，也不复制活跃 WAL。停机模式的进程管理、磁盘硬件可靠性、同账号恶意修改、备份加密、异机传输、定期调度、远端文件和整机恢复不由本工具承担。

## 官方依据

- [Node 22.13 的 `node:sqlite` 与只读 `DatabaseSync`](https://nodejs.org/download/release/v22.13.0/docs/api/sqlite.html)
- [Node 的 `sqlite.backup` 接口及版本记录](https://nodejs.org/docs/latest-v22.x/api/sqlite.html)：该接口从 22.16 起提供，因此本工具没有在 22.13 上直接导入它。
- [SQLite `VACUUM INTO`](https://www.sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause)：生成事务一致的独立数据库，清除已删除内容。
- [SQLite 只读 WAL 条件](https://www.sqlite.org/wal.html#read_only_databases)：解释辅助文件与只读访问的关系。

本工具使用官方文档说明的 SQLite 快照机制，并以本仓库的真实临时库测试验证实际行为，而不是只检查源码里有没有出现某个 SQL 字符串。
