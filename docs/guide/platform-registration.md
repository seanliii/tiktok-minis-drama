# 云端剧目登记：把已核验视频接到 TikTok 草稿

目标仍为 **Aurora Drama 日本首发**。本功能连接后台的已核验云视频和既有平台媒资审核流程，不用本地视频路径冒充平台视频，也不把“登记成功”写成“已审核／已上线”。

## 1. 运营操作

1. 在“上传素材”中完成云上传、服务器核验和“导入为草稿单集”。
2. 在剧目管理中保存封面、日文标题、简介和版权确认，检查集号从 1 起连续。
3. 打开新增的“新建／更新平台草稿”面板。
4. 填写**真实发行年份**、内容类型和连载状态。年份不默认填当前年；内容类型使用本轮官方说明中的 1=AIGC、2=漫剧、3=真人配音、4=真人本地化。
5. 点击“保存快照并执行”，明确确认将封面与剧集信息交给平台。只读打开页面不会自动外发。
6. 系统依次处理封面、建剧／更新、查询核对，并保存原任务 ID、Album ID 和版本。
7. 状态为“草稿登记已核对”后，点击“使用此版本继续审核配置”。系统把 ID／版本交给已有媒资面板并查询。
8. 审核、App 授权、在线版本、上架和本地发布仍分别确认。不会因建剧成功自动开始收费或发布。

一次初始登记的目标流程：

```text
已核验云视频 + 本地元数据
  → 保存不可变快照与请求编号
  → 为当前封面签发短期下载地址
  → 官方 Create Image
  → 官方 Create Album（仅首次）
  → 官方 Update Album（传入现有版本、元数据与集数）
  → 官方 Query Album（核对唯一版本、封面、语言、标题、集数与VID）
  → 已有媒资面板查询、提审与后续发布操作
```

## 2. 服务器需要的额外配置

除[云上传配置](/guide/cloud-upload)外，增加两项：

| 配置 | 含义 |
| --- | --- |
| `DRAMA_MEDIA_PUBLIC_ORIGIN` | 已部署的精确 HTTPS Origin，用于平台短期读取封面；不能带路径、查询串、账号密码或结尾斜杠 |
| `TIKTOK_MEDIA_JA_LANGUAGE_ID` | **由 TikTok 明确确认的日语整数枚举**，没有默认值；不能使用文档示例数字或测试里的 42 |

两项都留空，登记明确不可用；部分配置或格式错误会阻止应用启动。无真实配置时不“模拟开通”，不签发假地址，也不请求平台。

**北京时间 2026-10-19 再次读取官方 API 文档后，`language` 仍只有数字枚举说明，没有给出日语对应值。** 文档中的 `2` 是请求示例，不是日语映射证据；字幕使用的 `ja` 也不是剧目语言整数。开发须向平台确认准确值后再配置，不能要求运营猜数字。测试中的 42 只用于隔离服务，不得进入真实配置。

## 3. 封面不会因此长期公开

- 平台需要可下载的图片地址，但不意味着公开全部素材。
- 仅当前剧目的有效封面可签发，支持 PNG／JPEG／WebP，业务上限 5 MiB；不导出原始视频或字幕。
- 令牌由 32 字节随机数生成，有效期 15 分钟；数据库只保存摘要，不保存明文地址。
- 下载时再次核对管理员状态、版权、当前封面、内容版本、文件大小与 SHA-256；不是只检查令牌长度。
- 平台请求结束或失败后撤销本次授权；响应 `no-store`，现有 Nginx 模板关闭访问日志。其他代理／日志系统仍需对路径做脱敏，不能把下载地址写入工单或聊天。
- 备份只清除快照中的 `media_export_grants`，源库授权不受影响。换机不会带走临时下载权限。

## 4. 为什么分开保存任务、请求键和回执

“请求超时”既可能没有执行，也可能平台做完了、回执没送回来。因此不能按超时自动重建。

| 记录 | 用途 |
| --- | --- |
| 登记任务 | 固定本次剧目、版本、视频、封面和元数据快照 |
| 请求键绑定 | 每个被接受的请求编号都绑定原任务；相同快照合并也记录，重放旧编号不会重新写回旧资料 |
| 外部请求尝试／回执 | 将每次平台写操作与结果单独关联；任务执行时限与平台实际结果不是一回事 |

本地执行租约过期会停止后续写入，但已收到的有效迟到回执仍保存到对应原请求。成功、明确拒绝和未知分开处理，不因“查询也失败了”就解除此前写入的不确定性。

## 5. 各类失败怎么处理

| 状态／场景 | 处理 |
| --- | --- |
| 配置、版权、封面或集号不完整 | 不向平台发出请求；按具体原因修正 |
| 封面或建剧写入结果未知，尚无可查询 Album | 保留原任务，请平台核对；不能换请求编号盲目重建 |
| 更新受理结果未知，已有 Album | 仅查询同一 Album 与原快照，不重发更新 |
| 平台已生成新版本，但查询失败 | 继续只查询，不再次增加平台版本 |
| 查询期间又中断／租约过期 | 此前未决写入仍为未决，不会变成“可以安全重试” |
| 本地文案已改，但旧版本的单集 ID 还未核对 | 先只读核对旧快照，保存映射，再准备新快照；更新时传入已有单集 ID |
| 用户退出或换管理员 | 不向旧会话交付数据，不继续下一步；已收到的平台回执仍持久保存 |
| 迟到的明确拒绝 | 对应原请求保存拒绝事实，再允许明确重试；查询接口的拒绝不冒充原写请求被拒绝 |
| 其他媒资操作仍待核对 | 先完成原审核／上下架操作，避免与新登记互相覆盖 |

修改后继续使用已知的同一个 Album；没有让运营通过手填“已批准”跳过平台检查。

## 6. 本地验证与真实环境边界

新增测试覆盖真实 HTTP、SQLite、封面文件下载、已保存的回执及管理页面。只有外部 TikTok 响应和部分上游已核验视频记录是测试夹具，**没有连接真实云账号、上传商业影片、提交真实内容审核或执行扣款**。

浏览器验证包含：

- Chromium 与 WebKit 从填写资料到实际封面读取、建剧、登记集数、查询并使用既有审核面板。
- 更新回执丢失后重开页面，仅查询原 Album。
- 新版本已生成但查询失败，修改简介后先核对旧单集映射，再更新同一 Album。
- 小屏提示文字正常换行，控件触控高度和键盘焦点得到检查。

**空间、限定权限、真实上传以及 Aurora 的 BytePlus 账号绑定已完成后续核验**，见 [024](/progress/updates/2026-10-18-024-live-upload-hongkong-server)和[025](/progress/updates/2026-10-18-025-tiktok-binding-and-deployment)。不要按早期 021 记录重复办理。当前真实上线前仍需：准确的日语整数枚举、可控域名和 HTTPS 后端、VOD 播放域名及调度、平台视频查询、真实内容／字幕、官方环境联调及审核。代码中的“registered”不是平台的“approved”。
