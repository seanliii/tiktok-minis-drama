# 已有平台剧目的媒资业务流程

## 本轮范围与依据

本轮把**已有 TikTok 平台 album** 接入运营后台、服务器发布检查、公开片库、播放授权和新购买检查。不再只是一个独立 SDK。

支持：

- 为已有本地剧目填写真实平台 `album_id`，明确选择平台版本。
- 由服务器查询，按该版本同步审核、当前草稿版本、在线版本、上/下架状态和全部本地单集的 `episode_id` / `vid`。
- 提交该版本审核、选择已批准的在线版本、授权服务器配置的当前 App、请求平台上架或下架。
- 记录每次操作的请求 ID、原本地版本、平台版本、状态、时间和安全错误信息。
- 对平台写操作逐项确认；对未知结果阻止重发，对异步返回比较本地版本和操作 ID。

**尚未接入业务界面：新建云端剧目、文件上传/转存、云端内容编辑、字幕上传绑定、申诉和撤回审核。** SDK 中有部分底层接口不代表这些业务已经完成。不会自动创建空 album，也不会把 `language=2` 等示例数字当成日文枚举。本地“上传视频”仍是本地资产功能，不是上传到平台。

## 运营操作顺序

1. **准备本地内容。** 本地剧目必须已有从第 1 集开始连续排列的剧集；版权、封面、价格和免费集数仍由原发布流程检查。服务器需通过既有配置取得当前 App 的凭据，后台不会显示 Client Secret 或 AccessToken。
2. **打开“剧目管理 → 管理剧目 → 平台媒资”。** 页面初次加载只读本地记录，不自动调用平台。
3. **填写已有平台 Album ID 和关联平台版本，点击“关联并查询指定版本”。** Album ID 按字符串传输和保存，避免 19 位 ID 被 JavaScript 数字舍入。不会取返回列表的第一项，也不会默认选最高版本。
4. **需要提审时，点击“提交该版本审核”并确认。** 平台返回受理回执后显示“待查询确认”，不是“审核批准”。再点击查询读取实际结果。
5. **查询确认该版本已批准，再点击“设为在线版本”。** 写成功后再次查询，确认 `online_version` 是同一版本。当前草稿版本可以比选择的已批准版本新；不能把新草稿的状态和旧在线版本的单集混在一起。
6. **点击“授权当前App”并确认。** 目标 App 由服务器配置决定，调用者不能传其他 App。只接受 SDK 逐项校验后的成功授权回执。
7. **点击“平台上架”并确认，再查询。** 只有查询到 `publish_status=1`，且对应版本审核批准、在线版本相同，才满足平台上市条件。
8. **点击编辑器原有的“发布到本应用”。** 这一步不是平台提审或平台上架。服务器再次检查平台条件和原本地发布条件。

平台下架和本地下架是两件事：

- **“平台下架”** 请求真实平台停止服务，需要明确确认。请求已发出但尚未核对时，本地保守地停止交付；不会把原查询记录直接改写成“平台已下架”。再查询到 `publish_status=2` 才显示已下架。
- **“下架剧目”** 只改变本应用发布状态，不调用平台，不删除已购权益。

已发布的本地剧目允许重新查询相同 album 和版本；更换关联对象须先本地下架。旧生产数据只有手填 `approved` 和 ID、没有完整同步证据时也不能继续公开，需先本地下架、执行本流程，再重新发布。

## 发布、目录和播放共同检查什么

非 local 环境使用同一份服务器查询证据。仅设置 `platform_review_status='approved'` 不会放行。

必须同时满足：

1. 有服务器已成功查询的操作记录，属于相同 album、平台版本和当前 App。
2. 同步记录对应本地当前 `version`；本地内容不能在同步后又被修改。
3. 平台审核状态为 `2`（批准）或 `6`（申诉批准）。
4. 已关联的平台版本等于平台在线版本。
5. 平台 `publish_status=1`。
6. 有当前 App 的成功授权证据。
7. 本地剧集非空，集号从 1 连续排列；查询结果完整覆盖本地各集，无重复 `seq` 或 `episode_id`。每一集的本地 ID、集号、平台 `episode_id`、`vid` 与同步记录逐项相等。
8. 不存在需要继续同步/核对的状态，且不是样例内容。

这些条件用于原有的公开片库、详情、播放授权、公开封面/字幕和新购买检查。已有的 `ja` / `JP` 目录过滤、权限、版权、文件检查和价格校验仍然保留。

- **普通生产 PATCH 不能更新平台字段。** `platformAlbumId`、`platformReviewStatus`、`platformEpisodeId`、`byteplusVid` 是服务器同步字段。旧创建接口仍忽略传入的平台字段，不把它们写成平台证据。
- 修改本地剧目或单集会让同步记录过期。单纯本地上/下架不改变内容，只在原同步版本匹配时把同步版本一起推进。
- 查询只关联版本和播放所需映射，不把本地标题、简介或文件推送到云端；运营需核对选择的是同一部剧及正确版本。
- 媒资操作完成或明确失效导致本地版本更新时，面板通知父编辑器重读剧目。下一次保存或发布不能继续拿旧版本号。
- local 模式维持原有样例、文件发布和本地播放，不要求平台证据。即使在 local 模式手工使用本面板，平台写操作仍可能是外部真实操作，不是自动沙盒。

## 失败、未知与重启

请求 ID 是**本应用自己的操作编号**，不作为自造的 TikTok 幂等参数发送。

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| 处理中 | 请求存根已提交到 SQLite，可能正在获取 token 或请求平台 | 等待或刷新本地记录，不再提交另一份写请求 |
| 已确认 | 只读同步完成，或已取得明确的当前 App 授权回执 | 按实际审核/在线/上市状态继续下一步 |
| 待查询确认 | 平台已受理写请求，但其目标状态还没有被查询核对 | 查询同一 album 和版本 |
| 未知待核对 | 网络中断、超时、部分成功、回执不完整，或写请求中断后无人取得可信结果 | 只读查询核对；不可换请求 ID 重发 |
| 后续查询已核对 | 后续查询确认了目标状态 | 原操作不再执行 |
| 失败 | 查询失败，或 SDK 明确确认变更未提交/被平台拒绝 | 先读错误；同一请求 ID 只返回原记录 |
| 旧查询已丢弃 | 本地版本或后续操作已变化 | 读取最新本地版本，重新查询 |

实现上的关键点：

- 先在一个短 SQLite 事务中记录请求，提交后才开始外部 HTTP；等待网络期间不占用 SQLite 长事务。
- 同一请求 ID 重复到达，只返回原操作记录。把这个 ID 改成另一种操作、另一剧目或另一版本会被拒绝。
- 另一个 ID 也不能绕过未完成、未知或待核对的写请求。
- `submitting` 记录有 60 秒的本地租约。服务重启不会执行它；租约过期后，读取记录将中断的写请求标为未知。中断的只读查询可以新建一次查询。
- 每次异步应用结果，包括失败引起的失效处理，都比较**本地版本和最新操作 ID**。旧结果不能覆盖新内容；已被后续查询核对的记录也不能被迟到回执重新改成未知。
- SDK 对平台变更不自动重试。业务层也不自动重放。

### 什么能通过查询核对

可以根据同一 album / 版本的查询状态核对：提审、设在线版本、平台上架和下架。若查询仍与目标状态矛盾，则保留待核对记录，不因一次查询完成就解除重发限制。再次提审后若仍返回原来的拒绝状态，也不能据此证明新提审已经处理。

**现有官方查询结果不提供 App 授权状态。** 如果授权回执丢失，不能拿“审核通过”“已上架”或缺失字段来冒充授权成功。页面保留未知记录，需要向平台核实；本轮没有提供绕过核验的“强制成功”“清空未知”按钮，也没有虚构授权查询 API。

### 何时隐藏片库

- 同版本查询明确返回拒绝、下架、在线版本不匹配，或明确缺少该版本/本地所需剧集时，不再公开交付。
- 本地剧目的 `status` 可以仍是 `published`，但公开查询会排除它；后台保留本地发布记录并显示平台失败原因。
- **网络查询失败不会把上次的 `publish_status` 改成下架，也不会凭空撤掉上次有效的同步结果。**
- 运行时 Secret 缺失也不会伪造平台下架。发布、播放和支付各自在原有入口明确拒绝；支付仍保留“未提交失败”的订单记录，而不是误报产品不存在或请求已未知提交。
- 未知写操作期间保守停止交付，页面显示待核对，不伪造平台状态。
- 不删除订单、购入权益、历史或收藏。已验签的迟到支付回执和退款仍由原支付流程处理，不拿当前片库状态拒收已有订单的有效回执。

## 管理接口

所有接口仍使用原有管理员会话、同源检查和 `X-Requested-With: DramaVerseJP` 写入标记。

### 只读本地记录

```text
GET /api/admin/dramas/:id/platform-media
```

返回 `media`：本地版本、关联/当前/在线平台版本、审核和上下架状态、查询时间、当前 App 授权结果、阻止发布的原因、单集映射和操作历史。没有凭据、平台原始响应或视频 URL。

### 关联已有 album 并查询指定版本

```text
POST /api/admin/dramas/:id/platform-media/sync
```

```json
{
  "version": 3,
  "requestId": "c923bf93-ad0d-42e6-8f64-081d9f53029f",
  "albumId": "7637420375425239060",
  "platformVersion": 2
}
```

服务器查询该 album 的版本列表，但只采用明确指定的版本。返回 `media` 和本次 `operation`。重复只读查询应使用新请求 ID；重读相同 ID 只会取回旧记录，不再次外发。

### 经确认的平台写操作

```text
POST /api/admin/dramas/:id/platform-media/operations
```

```json
{
  "version": 4,
  "requestId": "8a363773-0b67-4df8-b18e-216b260b1930",
  "platformVersion": 2,
  "action": "submit_review",
  "confirmed": true
}
```

允许的 action：`submit_review`、`set_online`、`authorize_app`、`list`、`delist`。album 和目标 App 从服务器已同步关联及配置中取得，不接受任意 App、凭据或客户端声明的成功状态。

主要错误：

- `400`：参数错误、请求 ID 不合法、未确认写操作或试图 PATCH 只读平台字段。信息包含相关字段名。
- `409`：本地版本冲突、选择的平台版本不匹配、旧操作未核对、请求 ID 被改用或异步结果过时。
- `422`：指定平台版本不存在、查询必要字段不完整或剧集覆盖错误。
- `502`：平台查询失败、平台明确拒绝、部分成功或写结果未知。
- `503`：平台配置缺失或未满足原本地发布入口要求的完整平台条件。

## SDK 的 client_key 差异

官方 POST 参数表与 curl 示例并不完全一致，本轮没有把 query-only 当成确定契约：

- `album/update/`、字幕上传、字幕绑定、`album/status/`：按 POST 参数表在 JSON body 携带 `client_key`。
- 视频上传：按正文 curl 的 JSON body 示例携带 `client_key`。
- GET 查询：通过 query 传 `client_key`。
- 原 SDK 的业务 URL query key 暂时兼容保留。是否允许或要求这一冗余位置，仍需以后获授权的真实平台测试确认。
- 不给空创建 body、自身未定义该字段的操作臆造新的必填参数；不添加未经文档确认的重试/幂等接口。

相关 mock 合同测试同时检查 body key 和无损 ID。测试通过不等于平台线上契约已实测认证。

## 数据和验收

- `platform_media_operations`：持久操作存根、结果和后续核对关系。
