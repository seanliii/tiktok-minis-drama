# 订阅：分清当前观看资格和本次付款

Aurora 的正式订阅不再用本地“1000 Beans／30 天”测试商品代替。用户页通过平台读取套餐的价格字符串、币种和更新周期；本地测试 VIP 仍只用于离线演示。

**当前已接入代码：** 本人套餐和合同查询、持久操作、创建／重新启用、匹配付款通知、每期交易记录、取消／退款／撤销通知处理，以及平台当前会员恢复。用户端和管理员分别查看各自权限内的历史，管理员可以重处理已经验签保存的通知。

**验收边界：** 这些实现已在隔离数据、真实业务 HTTP 和浏览器中验证；外部 TikTok 接口和端内 SDK 使用测试替身。尚未部署云端服务，未执行官方 Sandbox、TikTok 真机、真实收费或平台审核。生产购买默认关闭，不能靠更改前端标志绕过；最终结果见 [018 阶段记录](/progress/updates/2026-10-17-018-subscription-ledger)。

## 1. 用户操作

用户从个人页或付费剧集页面进入 **Aurora VIP**：

1. 用本应用的 TikTok 账号登录，读取平台套餐与本人当前合同。
2. 已购买过的用户选择“購入を復元／現在の視聴権を確認”。这只查询当前权益，不创建订阅或重复收费。
3. 在服务端明确允许的环境中选择套餐后，系统保存操作、复核最新价格和现有合同，再调用创建或重新启用接口。测试和正式共用此流程，但档位、凭据、数据库和购买开关分开。
4. TikTok SDK 只使用服务端发回的交易编号。重开页面只读取原记录，不自动再次调用 SDK。
5. 查询结果与本次付款确认分开显示。平台查询或 SDK 返回成功，不会直接把这笔操作变成已付款订单。
6. 新操作最多进行五次只读通知确认。只有匹配通知已确认、没有退款或冲突、当前观看资格也恢复成功，才自动返回原观看入口。暂未确认时保留原记录，由用户继续查询，不再次购买。
7. 展开“手続き・契約情報”，在“購入・更新の履歴”中点“履歴を表示”查看每期交易。未知金额显示未确认；收到退款通知不等于已核实钱款到账。

取消自动续费和当前观看权益不是一回事。`is_renewal_normal=false` 可能是停止续费或付款异常，不能直接写成“会员已失效”；当前观看以有效的 `is_subscription_rights_valid` 及对应应用、档位、环境为依据。

### 解约／停止自动续费

订阅页标题下增加 **“解約・自動更新の停止”** 说明入口，不藏在交易技术详情里，也不要求先登录、购买或恢复会员后才能阅读。

- **TikTok Minis**：按照 TikTok 官方 Minis 条款的路径，进入 Minis 菜单页 → **Subscriptions** → 对应订阅 → **Cancel Subscription**，在平台完成操作。日本客户端的实际翻译、菜单层级和 Aurora 合同显示名仍须真机核对。
- **实际由 Apple 扣费**：使用购买时的 Apple Account，在 iPhone 设置 → 姓名 → 订阅 → 对应合同中取消；提供 Apple 官方通用订阅管理链接。
- **实际由 Google Play 扣费**：使用购买时的 Google 账户，在 Google Play 订阅管理中选择对应合同并取消；提供 Google 官方通用管理链接。
- **Web 或渠道不明**：先核对购买时的账单和 TikTok Minis 合同，不根据当前拿着 iPhone 或 Android 就推定购买渠道；找不到记录时按 TikTok 官方支持路径联系平台。

说明是纯静态内容。打开、关闭说明或访问官方管理页面，**不会调用本应用的取消／付款 API、恢复会话、改变会员或显示取消成功**。链接不拼接用户、交易号或合同号，也不携带本应用认证头和来源页地址；宿主不允许外跳时，仍可按页面内的设备步骤操作。

正常取消自动续费与退款是两种操作。取消不表示退回已付款项，也不能仅因关闭续费就提前撤销尚有效的已付观看资格。返回后“購入を復元”只核对当前观看资格，解约是否完成须以平台或实际购买渠道的合同页面为准。

本次未取得可依赖的官方 Minis 取消 SDK／取消 API 或合同级深链，因此没有编造接口，也没有使用已作废的订阅变更能力代替取消。**界面说明和本地测试不构成一次真实解约验收。**

## 2. 已有会员恢复观看

当前权益读取使用用户已经授权给本应用的服务端身份，不接收客户端传来的另一个用户编号、平台 token 或“我是 VIP”标志。

- 仅本应用明确配置的 VIP 档位可用于观看；预发布接受明确的 sandbox 来源，正式接受明确的 production 来源。缺失或冲突的环境不默认成正式。
- 同一订阅的档位、环境或当前权益记录互相矛盾时，结果为“未核实”，不会按任一 `true` 放行。一致重复或不同订阅中确有有效资格的正常情况仍受支持。
- 页面可使用最多 30 秒的本地观察；`refreshAt` 是**观察的新鲜度**，不是会员到期日。
- 请求受保护剧集的播放凭证时现场查询平台。已有单集／整剧购买和免费集不依赖订阅查询，因此订阅服务故障不会抹掉这些购买。
- 网络失败显示“暂未核实”，不是“未订阅”；明确的只读授权 401 会提示重新登录。
- 已验签订阅事件使旧观察过期。当前可解码八类通知，但未知字段、未绑定事件或不明时间单位仍不用于给会员加天数或撤销全部观看权。
- 新购单集／整剧前也检查当前会员，避免让已有 VIP 重复付费。原来未完成的单次购买仍按原请求号恢复，不因这项检查重建订单。

该流程不会伪造 `orders.status=paid`、退款记录或会员到期日期。**“现在允许观看”和“已经核销这笔付款”始终是两种证据。**

## 3. 配置官方无真钱测试

在独立预发布服务中，除现有真实 TikTok 身份、HTTPS 和通知配置外，显式填写：

```dotenv
DRAMA_MODE=staging
DRAMA_PAYMENT_MODE=tiktok
TIKTOK_SUBSCRIPTION_TIER_IDS=sandbox_499_1M,sandbox_1347_3M
TIKTOK_SUBSCRIPTION_SANDBOX=true
TIKTOK_SUBSCRIPTION_PRODUCTION=false
```

这些是官方文档列出的测试档位，不是本项目虚构的套餐编号。另有 `sandbox_699_1M`、`sandbox_1887_3M`。**展示价格仍以平台实际返回为准，不能从编号推算或自动换算成日元。**

官方指南说明测试档位不会发生真实支付，能够产生测试通知和续费事件。这与本机替身测试不同：实际运行还需要有效的 TikTok 测试用户、对应应用权限和平台能访问到的 HTTPS 通知地址。

- 正式环境不能配置 sandbox 档位或打开该测试开关。
- 没有档位且开关关闭时，正常保持“未配置”，不冒充开通。
- 凭据只保存在服务端，不使用 `VITE_` 前缀，不随 Minis 包上传。
- API 地址和信任域名配置完成后重新构建对应环境的前端包；本机能打包不证明真实环境已联通。

### 生产购买的独立开关

生产使用 `DRAMA_MODE=production`、`DRAMA_PAYMENT_MODE=tiktok` 和属于 Aurora 的正式档位，`TIKTOK_SUBSCRIPTION_SANDBOX=false`。新增 `TIKTOK_SUBSCRIPTION_PRODUCTION` 默认是 `false`，它控制是否接受新的创建／重新启用，不关闭已有合同、交易或当前权益的查询。

**不要现在就把它改成 `true`。** 必须先完成真实 HTTPS、应用凭据、商品与通知配置、官方测试和真机验收，再由发布负责人明确启用。预发布不能开启生产购买；生产不能使用 sandbox 档位，也不能同时开启两个购买开关。

## 4. 操作保存与异常恢复

| 情况 | 系统行为 |
| --- | --- |
| 重复点击、响应丢失后使用相同请求号 | 返回同一操作，不再次创建 |
| 新请求号遇到同一未完成操作 | 关联原操作，保留已接受的请求号 |
| 价格变化、原报价过期 | 不创建订阅，要求重新查看价格 |
| 最后一次 token 刷新期间退出或关闭测试 | 在真实业务 HTTP 发出前复核，明确按未发送处理 |
| 创建已发出，但超时或断开 | 保留未知结果，不自动换号再创建 |
| 用户退出后才收到创建回执 | 保存到原操作，不向失效会话交付 |
| 付款通知先于创建 HTTP 返回 | 先保存匹配确认，后到 HTTP 不覆盖它；即使 HTTP 失败，也不把已确认付款变成未创建 |
| 付款通知先于 SDK 领取 | 不重复发 SDK；继续只读核对原操作，再独立恢复当前观看资格 |
| 通知与 HTTP 指向不同交易 | 保留两份证据并显示冲突；冲突继续留在待办，不能换请求号再次购买 |
| 新操作检查中才出现旧冲突 | 在真正发送请求、领取 SDK 的边界再次检查，阻止重复购买；已在途的回执仍保存 |
| SDK 指令已领取 | 不重复领取或自动再次打开 |
| 查询返回 `SUCCESS`／`REFUNDED` | 保留为观察，不据此伪造本次成功通知或执行退款 |
| 已有会员恢复为有效 | 按当前资格观看，本次未核销操作仍独立保留 |

已保存交易编号的操作可以查询；没有编号且结果未知的操作，不能盲目认领该用户“最近一笔交易”。后续需要匹配的实际通知或平台侧核对。

## 5. 通知、每期交易与管理后台

通知先通过原始字节验签，再加密保存；解析和入账只使用这些已保存收件。合同、交易、用户、App 和环境必须相符，不能用客户端的“付款成功”或当前会员状态代替某一新订单的付款证据。

| 通知 | 记录什么 | 不做什么 |
| --- | --- | --- |
| create | 匹配本地操作，绑定合同，记录首期交易并确认原操作 | 不拿另一笔订单、另一用户或别的环境来确认 |
| renew | 用新的平台交易号记录新一期 | 不用首单编号去重掉所有续费 |
| reactivate | 确认恢复自动续费的对应操作 | 不凭这个动作增加一笔收费 |
| cancel | 记录关闭续费动作 | 不把取消动作的新交易号当原付款退款，不提前撤销已付权益 |
| onhold | 记录付款异常并要求刷新当前权益 | 不只凭状态名称判定会员已过期 |
| expire | 记录到期事实，当前观看仍重新查平台 | 不让迟到旧事件覆盖另一份新合同的有效资格 |
| refund | 记录对应历史交易的退款通知 | 不停止其他周期的当前会员，也不猜测到账情况 |
| revoke | 记录相应合同撤销和交易退款，重新核对观看资格 | 不把旧合同撤销套到新合同 |

金额可能缺失，留空并明确显示未知，不用报价补成实际扣款。`refund_price` 的单次／累计口径未明确，不逐条求和。外层事件时间使用文档明确的秒单位；`benefit_*` 等期间字段保留原始整数，不用位数猜单位、不计算假的会员到期日。

**后台入口：**

- 用户详情中的订阅核对面板增加每期流水，按交易而非通知条数分页。
- 订阅收件页展示已记录、重复、待绑定、环境待核对、格式错误、冲突或可重试错误。
- “重新处理”只重新读取已有验证收件，不提供手工改成已付、伪造通知或直接给会员加天数的接口。
- 待绑定／基础设施错误可由服务内消费者再次处理，重试时间持久保存。批次不重叠，停止服务时等待当前批次完成。
- 格式错误、未知事件、冲突仍保留证据供核对，不靠无限重试假装成功。

接口供开发联调，管理员接口仍需原有登录及来源校验：

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/subscriptions/history?limit=20&before=...` | 当前用户自己的每期历史 |
| `GET /api/admin/users/:id/subscription-history` | 管理员查看当前 App 用户的历史 |
| `POST /api/admin/subscription-events/:id/reprocess`，空 JSON 对象 | 重处理已验签保存的通知 |

原始加密通知、平台令牌、签名及密钥不随这些页面或接口公开返回。

## 6. 换机与恢复备份

备份保存原始业务快照；**恢复到新目录时**，额外执行：

- 尚无匹配确认凭据的未完成订阅操作改为待核对，保留原操作和交易编号，不重新创建或发放 SDK 指令。
- 已有确认凭据及每期流水保留，冲突和退款标记不删除；当前观看仍重新查平台，不能因有历史付款就永久发权。
- 报价过期，当前权益观察失效，恢复服务后重新查平台。
- 原源库和备份文件不变，已付单集订单和永久购买权益不撤销。

拍下快照之后，旧服务器可能又执行过操作。恢复旧快照不能证明那次外部操作没有发生。详见[备份恢复手册](/guide/backup-restore)。

## 7. 真正上线前仍要做什么

代码已经按实际读取到的原始公开订阅文档接入，不再以“缺少完整通知结构”为由停止整个功能。以下事项仍须真实平台验证，不能由本地替身测试代替：

1. BytePlus 账务与必要认证、视频空间和 Aurora 绑定；真实域名、HTTPS 业务服务、独立数据与备份。
2. Aurora 的真实 Team ID、该 App 的邮箱验证、必要确认和审核条件；旧 DramaVerseJP 的验证结果不自动迁移。
3. 日本正式商品档位、真实 TikTok 用户、通知地址和权限。核对当前官方 Sandbox 入口及测试档位是否对本 App 可用。
4. 实际通知中的 `content`、交易／合同关联字段、可选金额，以及缺失环境标识的处理；缺失环境不能默认成生产。
5. iOS／Android 上验证开通、取消、续费、欠费、到期、退款、撤销、重新启用、恢复购买和跨设备权益；覆盖重复／延迟通知及异常中断。
6. 在拟用云机器上做容量、备份恢复、监控和故障验证，完成应用、内容及版本审核后再发布日本版。

平台尚未明确的期间单位、拼写和退款金额口径继续保留原始值。没有足够依据前，不实现依赖这些未知值的到期推算或自动金额累计。

**用户系统不是另外买一个服务。** 账号、订单、会员、上传管理和片库都属于这套业务后台；视频另由平台要求的媒资服务及播放器承载。补卡只是开通云资源的一步，不等于业务已经部署、能收费或审核通过。
