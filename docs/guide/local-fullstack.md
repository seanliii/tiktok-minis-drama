# 前后台本地使用手册

**2026-10-14：项目已经有真实的业务服务、独立管理网页和接到服务端的日文用户网页，不再只有离线样例前端。**

**2026-10-15 更新：**测试付款额外确认已移除，新增与正式共用业务的预发布环境、主动平台状态核对和跨域部署配置。见[同流程配置与验证](/guide/environment-parity)及[009 更新](/progress/updates/2026-10-15-009-environment-parity)。

这里的“本地”指服务在开发机运行。用户、剧集、上传文件、订单、观看权益、收藏和历史会保存到磁盘；关掉网页不会清空。**付款使用明确标识的 Sandbox 测试流程，不扣真钱，不代表 TikTok 上线。**

## 1. 直接启动

进入源码中的 `app/tt-minis`，推荐使用更新到最新补丁的 **Node.js 22（最低 22.13）**，也接受 Node.js 24；本轮实际使用 22.23.2。22.12 及更早版本的内置 SQLite 默认行为不满足本服务启动方式：

```bash
npm ci
npm run local
```

`local` 会构建用户网页、管理员网页和服务器，再一起启动。不是只能查看的静态展示。

| 入口 | 默认地址 |
| --- | --- |
| 日文用户网页 | `http://127.0.0.1:5310/#/` |
| 中文运营管理页 | `http://localhost:5310/admin/` |
| 服务状态 | `http://127.0.0.1:5310/api/meta` |

**建议本地演示按表格区分 `localhost` 和 `127.0.0.1`**：它们访问同一个业务服务，但浏览器分别保存会话，方便同时打开管理员和普通用户。若两边都使用同一个主机名，切换登录会改变同一份 Cookie；这是正常的账户隔离，不是购买丢失。

首次启动自动创建随机管理员，凭据写在 **`app/tt-minis/.local/admin-credentials.txt`**。此文件仅本机用户可读、被 Git 忽略，不在任何交付包中。普通观众在用户页自行注册，不能使用管理员账号冒充普通观众。

- 已构建后再次启动：`npm start`，数据保留。
- 修改服务配置：将 `.env.example` 复制为 `.env`，按需填写。启动和初始化命令会读取它。
- 不要把 `.env`、凭据文件、数据库或上传的商业内容提交到仓库。
- 前后端开发时可分别运行 `npm run dev:server`、`npm run dev`、`npm run dev:admin`，默认端口是 5310、5173、5174。页面写请求必须来自配置允许的来源。

## 2. 运营怎么上传一部剧

1. 登录管理页 → **剧目管理 → 新建剧目**。
2. 填日文标题、简介、分类、标签、日本地区、免费集数、单集和整剧测试价格。勾选版权确认前，先确认有权使用作品、封面、视频和字幕。
3. 选择封面 → 点 **上传文件** → 等待服务器返回上传完成 → 创建剧目。
4. 点 **上传多集视频**，一次选择 `001.mp4`、`002.mp4` 等文件。系统按文件名数字排序，展示集数、标题和时长供检查。
5. 核对重复文件、集号和标题，勾选确认 → **开始上传并创建单集**。可看真实上传进度，取消失败项目后可重试。
6. 回到剧目管理，编辑单集；需要字幕时上传 UTF-8 **WebVTT（`.vtt`）** 并关联。
7. 确认封面、每集视频、从第 1 集开始的连续集号和版权资料齐全，点 **发布到本应用**。
8. 在日文用户网页刷新片库，检查首集、最后一集、字幕、免费边界及价格。

当前本地上传接受 **MP4、PNG/JPEG/WebP、UTF-8 WebVTT**，单个文件上限 **200 MiB**。这不是 BytePlus 云端的格式或大小上限。大规模长视频上传、转码和 CDN 不由本地服务代替。

### 常见情况

- **上传成功不等于单集创建成功。** 如果视频已入库但关联失败，重试会沿用已上传资产，不重复传整个文件。
- **选完文件还不算上传。** 必须点上传按钮并收到服务端成功结果。
- **草稿不会出现在用户片库。** 发布校验失败时会显示具体缺项。
- **已发布的内容不能直接改。** 先下架、再编辑、重新发布，避免用户看到半改完的数据。
- **有关联订单的单集不能删除。** 下架不会悄悄清空已购记录；恢复发布后仍按原有权益判断。
- 新增剧集是改数据库内容，**不用为每部剧重新开发一个 Mini，也不用为单纯上新重新打包这份用户网页**。TikTok 内容登记、审核和上架仍是独立步骤。

## 3. 用户账号和付费流程

```text
访客看片库 / 免费试看
        ↓
注册或登录普通用户账号
        ↓
选择单集 / 整剧 / 测试 VIP
        ↓
服务器建单并确定金额
        ↓
订单页明确显示“テスト決済・実際の請求はありません”
        ↓
点击一次「確認して購入」（确认购买）
        ↓
数据库记录付款 → 发放观看权益 → 才能播放付费集
```

- 本地账号使用邮箱和密码，但**没有邮箱验证，也没有冒充 TikTok 身份**。
- 密码以随机盐和 scrypt 处理；会话使用 HttpOnly Cookie，浏览器本地存储不保存密码或购买凭证。
- 个人页提供购买记录、服务器收藏、观看历史、续看、修改密码和退出登录。
- 改密码会撤销其他设备会话。退出后重新登录同一账号，服务器收藏、历史和权益仍在。
- 测试 VIP 默认 30 天，时间与价格由服务器设置；**不是自动续费订阅**。
- 取消订单、支付失败、页面弹出成功文字，都不能单独产生权益。
- 支付响应丢失时点 **支払い状況を再確認**；服务器已经收录的成功订单会恢复，不需要再买一单。

## 4. 管理员怎么查订单和退款

管理页 **订单** 可以按状态、订单号、用户搜索，显示服务器原始金额单位。`TEST_CREDITS` 不是日元或可提现收入。

本地 Sandbox 已付款订单可以点 **Sandbox 测试退款**，填写原因并确认。服务器记录退款、撤销本单权益；旧付费播放凭证也要重新接受检查。**这只是在测试账本中退款，没有转账。**

真实 TikTok 渠道没有模拟退款按钮，也不能由前端或本地管理员把真实订单改成“已付”。平台资金通知需要验签、订单匹配和服务端处理。部分追回与全额退款不同，不能不核对就撤销全部权益。

订单页下方还有独立的 **待核对追回通知**：逐条显示服务器收到的已验签通知、金额原文和内容指纹。相同指纹的两行可能是重复投递，**不代表发生两次退款**。金额单位及累计含义未确认时不换算、不自动累加，也不提供假“已处理”按钮。

真实订单如果已经发给平台但结果未知，会保持 **处理中**：页面禁止再次支付或取消，并继续查询同一订单。它不会因为本地过了几分钟就冒充“失败”再建一张单。**现已支持主动核对平台支付状态；仍未提供未核实契约的真实撤单或完整资金对账。查询不代替有效回执，也不能靠改本地状态解除。**

## 5. 实际架构与数据

```text
运营管理网页（admin/） ─┐
                       ├─ /api → Node.js 业务服务 → SQLite
日文用户网页（src/） ──┘                 └→ 私有 uploads 文件目录
                                         └→ 订单、权益、收藏、历史、审计

TikTok 平台包 → 官方 SDK / 官方播放器适配
                 └→ 真实凭据、媒资与支付联调另行验收
```

| 数据 | 位置 / 规则 |
| --- | --- |
| 数据库 | 默认 `.local/drama.sqlite`，不是 localStorage |
| 环境隔离 | 预发布默认 `.staging/`、正式默认 `.production/`；数据库保存环境标记，三者不能直接互换 |
| 封面、视频、字幕 | 默认 `.local/uploads/`；视频不提供可猜测的公开下载地址 |
| 管理员初始凭据 | `.local/admin-credentials.txt`，不会进入源码或运行包 |
| 登录会话 | 服务器保存令牌哈希；浏览器 Cookie 为 HttpOnly |
| TikTok 令牌 | 配置后以 AES-GCM 加密保存，只留在服务器 |
| 本地访客收藏与历史 | 仅此浏览器，不自动导入任何注册账号 |

数据库和上传文件必须一起备份。**备份前停止服务；不要只复制仍在写入的 SQLite 主文件，漏掉 WAL 或媒体文件。** 当前媒体记录涉及存储路径，换机器或换路径恢复需要额外迁移验证，不承诺任意目录直接恢复。

生产库的旧本地会话、样例内容、沙盒权益和本地视频入口不能作为正式访问来源。含测试痕迹的历史未标记数据库也会拒绝生产启动；拒绝时保留原数据，不自动删除或“清洗成生产”。

这是一个便于接手的**单节点服务**，不是已验证的多节点、大规模视频云或高可用生产系统。

## 6. 三类构建别混用

| 命令 | 产物 | 用途 |
| --- | --- | --- |
| `npm run build:preview` | `dist-preview/` | 独立离线前端样例；无真实服务、账号和付款 |
| `npm run build:fullstack` | `dist-service/`、`dist-admin/`、`dist-server/` | 可持久化的本地前后台完整服务 |
| `npm run build:minis` | `dist/` 和官方 CLI 候选 zip | TikTok 平台结构检查；不包含管理后台、数据库和测试视频 |

**GitHub Pages 只能承载项目文档或静态预览，不能运行这份 Node.js 业务服务。** 不要把管理后台加到 Pages，就误认为数据库和支付也上线了。

## 7. 一次跑完回归

```bash
npx playwright install chromium webkit
npm run test:all
npm run build:fullstack
npm run build:minis
npm run check:minis
npm audit
```

`test:all` 包含前端单测、服务端接口测试、离线双浏览器、独立管理页和真实全栈浏览器流程。全栈测试使用独立临时数据库，不会删除或修改开发者 `.local/` 数据。

对应源码、运行日志与最终数字见 [008 全栈验证记录](/progress/updates/2026-10-14-008-fullstack)。SDK 替身测试只是验证调用方式，不能冒充 TikTok 端内测试。

## 8. 真正上线前仍缺什么

这一节不是“全部甩给运营”。明确分成外部资料和开发联调：

| 责任 | 仍需完成 |
| --- | --- |
| 项目负责人 / 主体管理员 | 确认日本最终 App 与主体、真实 Apple Team ID、通用上线审批、成员权限；不改美国团队应用 |
| 内容 / 版权 / 日本运营 | 提供真正可在日本发行的片源、封面、日文字幕与内容资料；样例视频不能上线 |
| 部署负责人 + 开发 | 真实 HTTPS API、数据库与存储、备份；已有精确来源跨域与Cookie配置，仍需确定 Mini 实际来源和真机策略，不能声称只填域名就一定可用 |
| 媒资管理员 + 开发 | BytePlus 账号和空间、平台绑定、素材上传与剧目登记、审核 / 上下架同步。当前本地发布不自动提交 TikTok；真实平台状态同步仍需实现并联调 |
| 支付配置负责人 + 开发 | 真实 Beans 商品、回调地址、测试名单；已有主动状态核对，仍需真实端内验证、完整对账 / 真实撤单与部分追回处理。真实订阅还需要 SKU 和生命周期实现，当前不是只填 SKU 即可使用 |
| QA / 日本测试人员 | Android、iOS、TikTok 端内、日本环境、弱网、字幕、支付取消 / 延迟 / 退款及订阅测试 |
| 发布负责人 | 审核资料和联调完成后才上传、扫码、提审和发布；本次未自动执行 |

**当前可以验收“真实本地前后台业务”，不能据此宣称“已经可以在日本向真实用户收款”。**
