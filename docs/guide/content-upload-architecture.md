# 传短剧需要什么后台

::: tip 已有后续实现
本文保留 2026-10-14 的架构调研背景。后续已经实现本地业务服务、独立上传管理网页和用户账号／订单／权益，见[实际使用手册](/guide/local-fullstack)和[008 验证记录](/progress/updates/2026-10-14-008-fullstack)。下文的“建议开发”是调研当时状态；BytePlus、平台媒资审核与真实订阅仍需按交付清单继续接入，不代表全部生产架构已完成。
:::

调研日期：**2026-10-14**。这是架构建议，不是已经实现的后台；本轮未搭建服务、购买云资源、上传影片或修改平台配置。

## 1. 先说结论

1. **发布短剧不一定要开发 Minis。** 普通发片、符合资格的付费 Series、Drama Center 的剧集发行，都是与自建 Minis 不同的路线。
2. **一部新剧不需要一个新 Minis。** 如果继续经营 DramaVerseJP，应让同一个应用展示多部剧，剧与集由接口和数据库管理。
3. **继续自营片库与收费应用，需要服务端能力；方便运营传剧，建议再加轻量管理网页。** 服务端与运营网页不是一回事，也不必做成庞大的系统。
4. **不用自己再造视频云。** 用 BytePlus 处理视频上传、存储和转码，用 TikTok 处理相关内容审核及平台播放控制；我们管理片库、运营流程、用户、订单与观看权益。
5. **最小方案不是先做一个“大上传平台”。** 可先用 BytePlus 现成控制台上传视频，自己的后台负责关联视频编号、剧集信息、提审／上架和用户业务，稳定后再增加批量直传。

可以把它理解成：**Minis 是影院前厅，运营管理页是排片办公室，业务后端是售票与检票系统，BytePlus 是影片仓库，TikTok 是发行与端内平台。**

## 2. 不同经营目标对应不同路线

| 目标 | 路线 | 是否必须开发 Minis | 后台／准入边界 |
| --- | --- | --- | --- |
| 发布免费短剧、切片或预告，先验证内容 | TikTok 普通账号发片 | 不需要 | 用平台发布工具；内容合规、版权和账号能力仍需确认 |
| 直接销售内容合集 | 创作者 **TikTok Series** | 不需要 | 日本有历史官方上线公告，但不能据此保证当前具体账号具备资格 |
| 向 TikTok 提供剧集，利用其分发与广告解锁 | **Drama Center → Drama Series** | 不需要自建 Mini 应用 | 官方要求企业验证、供应商／收款信息、签约和账号权限等；本账号是否符合日本准入尚未核实 |
| 自有品牌、可控片库、选集、单集解锁、会员体验 | 自建 **TikTok Minis** | 需要开发或采用经过核实的服务商方案 | 需要平台准入、客户端接入及业务服务端；可自己做或使用服务商，不是全部从零造 |
| 独立 iOS／Android 短剧 App | 独立 App＋共享业务后端 | 不需要 Minis，但需要 App 开发和商店流程 | 可共享片库管理，登录、收据校验、收费和播放接入按渠道分别实现 |

### 三个相似名称不能混用

- **TikTok Series**：创作者付费合集产品。日本官方在 **2023-06-27** 发布过上线公告；这是历史地区依据，不是我们当前账号的开通证明。[S6]
- **Drama Series**：官方微短剧发行文档介绍的剧集形式；该文档 **2026 年 9 月版**明确介绍看广告解锁后续内容，不能自行推断为同一个付费合集产品。[S5]
- **TikTok Minis**：我们正在开发的端内应用，带有自己的页面与业务接入。[S5]

**建议决策：**如果目的只是“之后方便传剧”，先让业务负责人确认 Drama Center 是否可用。如果目标是“经营自己的短剧看片应用”，保留现有 Minis，补业务后端和轻量运营管理页。开发不能仅凭营销文章替业务决定渠道。

## 3. 哪些“后台”已经有，哪些需要我们补

| 部分 | 平台已经提供 | 不应误认为已经提供 |
| --- | --- | --- |
| TikTok Developer Portal | 应用资料、代码版本、成员权限、开发配置、营收配置及媒体账号绑定等 | 自己产品的完整片库编辑器、订单系统、会员与观看历史服务 |
| TikTok 媒资接口 | 视频／图片／字幕、剧目版本、审核、应用授权、线上版本和上下架操作 | 每个开发者都会自动获得一套符合自己工作流的运营管理网页 |
| BytePlus VOD | 视频控制台、上传 SDK、视频托管、处理与分发能力 | TikTok 内容审核通过、自家用户已购买、面向日本的版权自动齐备 |
| 我们的运营管理页 | **建议开发**：剧集信息、排序、免费范围、任务与审核状态、上架操作 | 不必做成 Minis；普通内部 PC 网页即可 |
| 我们的业务后端 | **需要实现或接入**：身份、片库、订单、权益、同步、密钥保护、异步任务 | 不是在浏览器里保存几个 JSON 或把密钥放到前端 |

**这次最关键的官方发现：**TikTok 当前媒体文档明确要求通过 Open API 完成媒体上传、审核、上架等流程。BytePlus 可用网页控制台上传文件，但这不等于自动完成 TikTok 剧目登记与上线。[S1][S2][S4]

官方收费接入也明确要求后端建单、验证支付通知、避免重复发货并提供订单状态。前端“支付面板成功”不能替代最终权益到账。[S3]

## 4. 推荐架构：一个业务服务，不急着拆很多系统

以下是**建议设计**，不是现有实现：

```text
运营同学（电脑）
        │
        ▼
轻量运营管理页
  新建剧 / 导入集数 / 封面字幕 / 免费范围 / 提审上架
        │
        ▼
业务 API 服务 ─────────── 数据库
  ├─ 片库与日本发布设置       剧 / 集 / 版本 / 渠道映射
  ├─ 登录与观看历史           用户 / 观看进度 / 收藏
  ├─ 订单与会员权益           订单 / 支付通知 / 权益记录
  └─ 上传与审核任务           任务状态 / 重试 / 操作记录
        │                           ▲
        ├─ TikTok 媒资接口            │
        │    登记 / 审核 / 授权 / 上下架
        ├─ BytePlus API / 上传凭证
        └─ TikTok 登录 / 支付 API 与通知

日本用户 → DramaVerseJP Minis → 业务 API 查询剧目与观看资格
                      │
                      └→ 官方 VePlayer → 平台校验并播放 BytePlus 媒体
```

### 视频与业务数据走不同的路

- **视频文件**：运营浏览器拿短时上传凭证后，直接传 BytePlus，不让大量 GB 视频先挤过自己的普通业务服务器。
- **业务数据**：标题、集序、视频编号、审核状态、价格与权益存在自己的数据库，通过业务 API 查询和修改。
- **秘密资料**：TikTok Client Secret、BytePlus AK/SK、长期令牌放服务端秘密配置；运营和观众都不接触它们。
- **播放控制**：后端检查是否免费／已购／会员有权；TikTok／VePlayer 再检查媒资与平台资格。两者不能互相代替。
- **状态同步**：BytePlus 使用其支持的上传事件通知；TikTok 审核等状态按官方实际提供的回调或查询接口同步，不假设每一步都有 webhook。

BytePlus 官方上传 SDK 支持浏览器上传、临时凭证，以及可启用的分片／断点恢复；这些能力应直接接入，不再自己实现一套视频上传协议。[S4]

### 先不要做的事

不自建转码集群、CDN、视频播放器内核；不为每部剧建应用；不先拆成多套微服务；不把“免费／已购”存在本地当正式权益；不让运营持有各平台管理员密码操作日常片库。

**部署建议：**优先沿用团队现有技术栈与云环境。没有现成后端时，一个与当前 TypeScript 前端配套的业务服务、一个托管关系数据库、一个后台任务执行进程即可起步。任务状态可以先放数据库，不必为了批量上传立刻引入复杂队列体系。

## 5. 运营以后怎么上一部新剧

以下用“新剧共 60 集”说明**建议的管理流程**，不是说平台自动提供这套界面：

1. 运营在后台点 **新建剧目**：填日文标题、简介、真人／动画类型、字幕／配音、版权地区与期限、总集数和免费范围。
2. **上传或导入视频**：初期可在 BytePlus 控制台上传后导入视频 ID；下一阶段支持在我们后台选一个文件夹批量上传。
3. 后台识别 `001.mp4`、`002.mp4` 等集序，列出重复、缺集、格式或字幕错误，要求运营确认，而不是按字符串把第10集排在第2集前。
4. 系统记录上传任务，等待媒体处理完成；创建／更新 TikTok 的剧目与集信息，关联 `byteplus_vid`、封面和字幕。
5. 运营点击 **提交内容审核**。页面显示真实审核进度和失败原因，上传成功或 HTTP 200 都不能冒充过审。
6. 审核通过后，选择正确的线上内容版本，并完成平台授权／上架。
7. 自己的片库再设置日本发布、展示排序与收费规则；确认平台可播放后，Mini 查询片库时展示新剧。
8. 运营实际检查首集、最后一集、字幕与付费边界；有问题可下架该版本并保留操作记录。

**通常不需要重新发一版 Mini 代码：前提是片库从 API 动态读取，而且只是新增／更新内容，不是在增加新的程序功能。内容审核、版本与上架流程仍然要走。**

官方媒资 API 将应用、剧目、单集分别建模，并提供独立的内容版本、提审、线上版本与上下架接口；`album/update` 会生成新版本，不原地覆盖历史版本。[S2]

## 6. ID 和权限必须分清

| 编号／状态 | 含义 |
| --- | --- |
| App ID / Client Key | 哪个 Minis 应用 |
| 我们自己的 drama_id / episode_id | 业务片库记录；应与平台编号分别保存 |
| TikTok album_id / episode_id | 哪部剧、哪一集及对应平台内容 |
| BytePlus vid | 视频云里的哪个媒体文件 |
| 内容 review_status / online_version | 哪个内容版本通过审核并被选择上线 |
| 用户 entitlement | 哪个用户通过免费、购买或会员取得什么观看权 |

平台接口中的 **album authorize** 是把内容授权给指定 `client_key`，**不是给消费者发放购买权益**。同一个 BytePlus 账号允许绑定多个 App，但内容本身仍要满足单剧同账号同空间、渠道授权和审核条件；商业版权也不会因此自动跨主体转移。[S1][S2]

实施时建议平台长整型 ID 在浏览器与 JSON 里按字符串处理，避免 JavaScript 数值精度损失；每次运营动作带上目标应用和内容版本，防止将 Aurora Drama 的内容状态套到 DramaVerseJP。

## 7. 最小开发范围与先后顺序

| 阶段 | 开发范围 | 通过标准 |
| --- | --- | --- |
| A：先让一部合法剧能联调 | API＋数据库与真实身份；用 BytePlus 控制台上传；小型管理页导入媒体ID；内容登记／审核／上架；Mini 改为读真实片库并接 VePlayer | 在有权限的测试环境显示真实内容；新增下一部剧不修改客户端源码；不将内容上架当作应用已发布 |
| B：让运营可以持续传剧 | 批量直传、字幕封面、缺集检查、任务续传／重试、审核反馈、排期、上下架和操作日志 | 运营不需要开发手工调用接口；中断后不重复创建影片或乱序 |
| C：正式收费运营 | 建单、支付通知、权益、订阅／退款、跨设备历史；可在 A/B 期间并行实现 | 取消不发权、重复通知不重复发货、退款／到期与实际权益一致；业务及平台审核齐备后才公开收费 |
| D：更多渠道 | 共享片库管理，分别接独立 App、其他平台渠道 | 内容管理不重复造，账号／支付／播放能力与地区规则按渠道隔离 |

**A/B/C 都包含开发工作，不能把“后台需要补”全部交给运营。** 运营提供素材、规则、账号权限和准入结果；开发实现接口、页面和状态处理；QA 负责端内与异常流程验证。

轻量管理网页可以先只做这些入口：**剧目列表、集数与素材、上传任务、审核发布、收费规则、订单／用户查询**。首期不需要复杂推荐算法、报表中心、供应商结算系统或多品牌后台。

## 8. 当前项目离这套架构还有什么差距

本轮重新读取源码确认：

- `app/tt-minis/src/utils/mock.ts` 仍是写在代码里的样例目录。
- `app/tt-minis/src/views/Home.vue` 直接导入该目录，不是动态内容 API。
- `app/tt-minis/src/stores/user.ts` 明确保持访客状态，真实服务端未接入。
- `app/tt-minis/src/views/Player.vue` 在平台环境显示正式媒资准备中，浏览器视频只用于预览。
- 当前项目没有已经部署的运营 CMS 或业务后端。

因此，**“前端离线体验通过”与“运营能自行上传新剧、正式收费”之间，差的正是内容后台、业务服务端及平台联调**。不是继续往 `mock.ts` 里加条目就算完成。

不建议推倒现有前端。下一阶段重点应从“新增几个页面”转到“动态片库＋内容上传管理＋正式播放”，然后接完整收费业务。

## 9. 本轮核实与未核实

**已核实：**当前项目源码、TikTok 媒资/API/播放器/收费文档、BytePlus 上传说明、TikTok 两种短剧发行方式，以及日本付费 Series 的历史官方公告。

**未核实：**我们账号的 Drama Center 准入、日本地区具体收费能力、BytePlus 商业合同与报价、目标 App 最终选择、现有团队后台可接入程度。未实际上传短剧，也未调用任何会创建订单、提审或上架的接口。

还有几个文档实现细节必须在开发时再次对照实际接口：媒资创建接口示例不完整、语言枚举不能凭示例数字猜日本值、字幕要求有翻译歧义；不根据空请求示例直接写生产实现。
