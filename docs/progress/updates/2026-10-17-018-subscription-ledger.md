## 1. 本轮已实现并验证

### 付款通知与每期记录

- 接收入口先验证原始字节签名，再加密保存；解析器和账本只处理这些已保存收件。
- 支持 create、renew、reactivate、cancel、onhold、expire、refund、revoke 八类通知。
- 首次开通确认必须匹配原操作和交易，核对用户、App、环境和合同；SDK 回调、交易查询 `SUCCESS` 或已有会员均不能代替这笔付款的匹配通知。
- 续费用新的交易号记录新一期；重新启用和关闭续费只记动作，不多记一次收费。
- 历史交易退款与当前合同撤销分开；历史退款不直接终止当前会员，观看仍现场查询平台当前权益。
- 未提供的金额保持未知，不用报价补实际扣款；退款金额口径不明确时不逐条累计。
- 外层事件时间按已明确的秒单位处理；未明确单位的期间字段无损保留，不计算假的到期日。

### 用户与后台

- 用户展开“手続き・契約情報”，可读取自己的“購入・更新の履歴”，按交易分页，保留读取失败后的原页。
- 新操作最多五次只读确认；匹配通知、当前观看资格都核实后，才返回安全的原观看入口。
- 退出、换号或页面离开会取消原读取，旧账号的迟到响应不能重新出现在新账号页面。
- 管理员可查看用户每期流水、通知处理状态，明确点击后重处理已有收件；没有手工改成已付、伪造通知或给正式会员加天数的入口。
- 收件待绑定、环境待核对和基础设施失败有持久重试时间；服务内消费者负责后续处理，退出时等待当前批次结束。

使用和配置见[订阅工作流手册](/guide/subscription-workflow)。

## 2. 这轮实际修复了哪些问题

### 不能让冲突订单从待办消失

原来操作已经带确认指针、但又出现交易冲突时，界面显示冲突，待办查询却可能把它排除。换一个请求号就存在再次购买风险。

现在：

1. 未解决冲突仍保留并优先显示。
2. 创建预约、价格复核后、真正发出平台请求前及领取 SDK 时都核对同一身份的未解决冲突。
3. 已在途请求的迟到回执仍保存；不会为了阻止重复下单而把冲突证据丢掉。
4. HTTP 返回的另一交易编号单独保存，不覆盖已确认的原交易。

三个新增反例先实际失败，再修复；相关接口专项从 **3 失败／11 通过** 变为 **14／14 通过**。独立只读复核确认原问题已关闭；该复核本身未重跑测试，测试结论来自主任务实际执行。

### 通知比 SDK 领取更早到达

如果通知已经确认，服务端会拒绝再次领取 SDK。用户页现在转为继续读取原操作、核对当前权益，不重复创建或重开 SDK。该场景已加入真实 Vue／业务 HTTP 的浏览器测试。

### 全量回归中的旧断言与上传等待

第一次全量回归在后台套件实际出现 **3 项失败**：

- 两项仍期待旧的统一“尚未履约”文案，改为检查当前真实的“已接收，尚无处理结果”，并额外断言没有显示已入账。
- 一项自动化在上传控件仍禁用时强行设置文件。按 Playwright 的实际行为，`setInputFiles` 不等待 Enabled；现在先等待用户真正可操作的控件，再执行原来的真实上传、发布、付款和退款流程。

没有删除业务权限、文件上传限制或付费校验。修正后后台 **25／25 通过**，随后重新执行了下一节的完整回归。

辅助外部监督 CLI 两次在 180 秒后超时，**未计入通过**；源码复核、失败反例和真实测试结果分别保留。
